# 普通照片求解：修复与验收

## 范围

当前回归目标是 `IMG_8695.jpg`–`IMG_8708.jpg`：14 张普通数独屏幕的实拍照片，包含透视、反光和摩尔纹。`IMG_8709.jpg`–`IMG_8712.jpg` 是装饰边框照片，单独记录，不要求本轮通过。

这是已知图片回归，不是任意相机、纸质数独、弯曲纸张的泛化证明。下一轮需要从不同设备/场景采集未参与训练或调参的新照片。所有照片标注均由助手逐格目视复核；不是由求解器或 CNN 输出反填标签。应保留人工再次复核的机会。

## 已定位并修复的问题

1. **OCR 训练裁切错误**：旧 release 来源 run 使用 `--use-yolo=True`。从 Git 恢复的历史 YOLO ONNX 输出 `[1,300,38]`，元数据 `kpt_shape=[16,2]`；训练代码默认按 4 点读取，取到了同一顶边上的四个点。以 `sudoku_5.jpg` 为例，错误四角面积约 2,886 px²，正确外角面积约 2,262,328 px²。新 OCR 训练只使用版本控制内的 GT 四角，不再走 YOLO 或 Corner 推断裁切。
2. **数字标注错位/错误**：18 张照片中修改了 17 张数字标注，1 张确认无误。`IMG_8700.jpg` 原图 r1 为 `300049000`，旧 JSON 为 `020910500`，显然不是同一棋盘。修订后 18 张标签均无冲突且有唯一解；唯一解只是辅助校验，不是标签的来源。`data/labels/sudoku_label_sources.json` 记录复核来源。
3. **四角标注错误**：修正 `IMG_8698.jpg`。OpenCV 候选经目视检查与原图网格一致后写入 `data/labels/sudoku_corners.csv`；其余角点从已有标注迁入。OCR 训练/评估不再依赖 gitignored 的 `data/corner_cnn/images/` 副本。
4. **照片预处理和阈值**：原有 CLAHE + cell Otsu 会把缓慢光照变化放大成黑块。现在先在整个棋盘上做局部阈值，再切格。低于数字阈值的预测不能在二次识别失败后被无条件保留为 given；单格与批量共用选择逻辑。
5. **验收和发布**：Corner 输出须通过已有网格线规则性检查，否则允许 OpenCV 接管；OCR 按棋盘分组切分，不拆散同图或重复 givens；最佳 checkpoint 深拷贝，防止被后续训练覆盖；导出验证 PyTorch/ONNX 数值一致；发布必须通过 14 张普通照片及 2 张截图的 exact-match 门禁，失败不更换 canonical。

`visual-sudoku-route-review.md` 中的 `5/222` 是对旧错误标签的比较值，**不能作为真实照片 OCR 准确率**。保留该记录用于追踪诊断过程，不作为新旧模型收益的分母。

## 复现

普通照片严格验收（必须同时整盘识别正确、求解答案正确）：

```bash
uv run python scripts/eval_cnn_ocr.py \
  --cnn-model models/releases/sudoku_digit_cnn.onnx \
  --detector auto --strict \
  --image-pattern 'IMG_86*.jpg' 'IMG_870[0-8].jpg'
```

Web 真实上传 → 识别 → 求解回归：

```bash
uv run --extra dev pytest tests/test_photo_solver.py -q
```

训练（自动记录数据哈希和 `split.json`）：

```bash
MLFLOW_TRACKING_URI="file://$PWD/mlruns" \
  uv run --extra ml python scripts/train_cnn_ocr.py \
  --version 3.5.2 --epochs 60 --patience 20
```

发布时仍需显式指定训练 run：

```bash
MLFLOW_TRACKING_URI="file://$PWD/mlruns" \
  uv run --extra ml python scripts/release_model.py cnn \
  --run-id <VERIFIED_RUN_ID> --version <YYYYMMDD.N>
```

发布元数据保留类别顺序、输入尺寸、训练版本和预处理版本，OCR reader 会解析 canonical symlink 邻接的真实 sidecar。

## 2026-10-14：检测修复（装饰边框、翻拍摩尔纹）

两个检测缺陷，均与 OCR 模型无关：

1. **全分辨率摩尔纹**（`IMG_9749`，测试集）：12MP 翻拍屏幕时，网格外框与相邻边框粘连，检测器退回单个 3×3 宫。OpenCV 检测改为依次尝试原图和 ≤1280px 宽副本，取第一个网格线规整的结果。只缩放不行：会让 8 张纸质照片失败。
2. **竹子装饰边框**（`sudoku_21`、`IMG_8709`–`IMG_8712`）：候选要么是边框，要么是中间的宫，原来的修正只会向内收缩。`snap_to_lattice` 在候选四边形周围拉正，并拟合每个方向 10 条等距格线：边框向内收缩；宫先按自身 4 条线重新拟合，再向外延伸 6 格，并且必须落在宫边界上。每条边界线在两条带中分别测量，因此透视也能被修正。

|---|---|---|
| 40 张图完整流程，错误解 | 35/40，0 | 39/40，0 |
| 测试集 | 28/29 → 加入 4 张新照片后为 32/33 | 32/33 |

## Corner CNN release 20261014.2：热力图 + 合成数据

`20261014.1` 的根本问题出在结构：它把全局平均池化后的特征直接回归成 8 个坐标，池化丢掉了"特征在哪里"的信息，所以连训练图都学不好。新结构（训练版本 2.0.0）在 MobileNetV3-Small 上加一个小型 FPN，在 1/4 分辨率上为每个角点输出一张热力图，再用 soft-argmax 得到亚像素坐标。损失是坐标 L1 加上对高斯目标的 KL。ONNX 输出仍是 8 个坐标，所以检测器和 ML Backend 不用改。

训练用 6000 张合成图（`scripts/synth_corner_data.py`）。生成器覆盖了真实图里的各种情况：
- 干扰物：数字键盘、相邻的网格、装饰边框、网页 UI、文字。
- 网格样式：线宽、颜色、深色主题、宫格底色、高亮格。
- 成像方式：截图和翻拍，翻拍时加透视、纸面弯曲、反光、阴影、摩尔纹、模糊。

合成图只用于训练，挑选模型只看真实图的验证集（11 张）：

| 验证集 | 角点中位误差 | 解出 |
|---|---|---|
| 回归结构 20261014.1 | 4.5% | 4/11 |
| 热力图，只用真实图 | 1.35% | 8/11 |
| 热力图 + 合成图 | 1.24% | 10/11 |

选定后，在 15 张留出测试图上只评估了一次：

| 15 张测试图 | 20261014.1 | 20261014.2 |
|---|---|---|
| 角点中位误差 | 6.2% | 1.02% |
| 误差 ≤ 3% | 5 | 15 |
| 通过规整性检查 | 6 | 14 |
| 单独使用时解出 | 5 | 13 |

没解出的 2 张：`flickr-sudoku-stumper` 本身有多解，按预期不应给出解；`gnome-ru` 的角点误差为 2.7%。装在塑料套里的卡片 OpenCV 至今解不出，新模型能解出。

Web 检测链的结果不变，75 张中仍解出 73 张、0 错误，因为只有 OpenCV 返回空时才会轮到 Corner CNN。另外，`snap_to_lattice` 对浅色细线的截图拟合不出格线（每格只采样 30px，阈值后细线丢失），所以 snap 后能解出的数量反而比直接用预测少。这是 snap 原有的局限。

## Web 读取顺序：OpenCV 解不出时改用 Corner CNN

OpenCV 和 Corner CNN 各自能解出对方解不出的图：Corner CNN 能解反光照片 `IMG_8712` 和塑料套卡片，OpenCV 能解 `gnome-ru` 和 `nyt-medium-1-wide`。原来的检测链只在 OpenCV 什么都没检测到时才调用 Corner CNN，而 OpenCV 在这两张图上都检测到了网格，只是解不出来，所以 Corner CNN 从来没有机会运行。

`routes.read_image` 改为：OpenCV 检测到的网格能唯一求解就直接返回；否则用 Corner CNN 的角点重新识别一次。这次重试不经过规整性检查，因为这项检查会把 14 张有摩尔纹的照片上本来准确的角点也拒掉，而"唯一解"本身就是更严格的接受标准。两次都解不出时，返回 OpenCV 的结果；OpenCV 没有检测到网格时，只有 Corner CNN 的四边形通过规整性检查才会返回，所以不含数独的图片仍然会提示"未检测到网格"。删除了 `ChainDetector`。

| 检查 | 修改前 | 修改后 |
|---|---|---|
| 75 张标注图，web 流程，错误解 | 73/75，0 | 75/75（含 1 张按预期判为多解），0 |
| 测试集 | 14/15 | 15/15 |
| 14 张普通照片 `--strict` | 14/14 | 14/14 |

只有 OpenCV 解不出的图才会多走一次 OCR。
